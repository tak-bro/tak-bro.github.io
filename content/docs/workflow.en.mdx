When I hand work to a coding agent, it goes down the same path every time. The size of the task picks the steps, a plan file holds the work and the checks, every slice passes a review gate, and it stops at a draft PR. I do the merge. Each step is a skill (a slash command) in the [Agent config](./agent-config.mdx) repo. That repo is private, so you cannot use it as is. The size table and the review loop rules are shown in full below.

## How it works

### Size picks the steps

Not every task runs every step. The number of files that change sets the size, and each size has its own steps.

| Size | When | Steps |
|---|---|---|
| S | 1–2 files | Implement → review → ship (for a bug, investigate first) |
| M | 3–10 files | Explore → plan → slice loop → whole-branch review → ship |
| L | 10+ files | M, plus a scope review before and one cleanup pass (`/simplify`) after the slice loop |
| XL | I don't yet know what to decide | Settle the decisions with questions first, then plan → same as L |

Even with few files, a change that touches authentication, authorization, user input, DB queries, file paths, external APIs, cryptography, secrets, or a public API or contract is at least M. When the plan has 3 or more slices, or creates a new module, service, or package, one more review with an engineering lens (`/plan-eng-review`) runs after the plan. Catching slice boundaries and failure cases before any code is cheaper.

With `/orch`, the agent makes this choice. Its first line declares the kind of task (add, change, fix, refine), the size, the done criterion, and the command that measures it. Then it runs the steps through to the end. If the declaration is wrong, I correct that line.

### The plan is a file

For M and up, the plan is written to `.claude/<date>/PLAN-<time>.md` in the repo. That file is the whole state of the task. If the session breaks or the context is compacted, the agent reads the file again and continues.

- **Slice queue** — a table that splits the work into vertical slices. A slice is not one layer of the stack but a narrow path that works end to end, and it can be checked on its own. The checkboxes are the progress.
- **Acceptance contract** — one line per done criterion, each tied to the command that measures it. Before implementing, the agent runs the contract checks to confirm they actually fail. A contract check that passes from the start measures nothing. Once implementation starts, the contract is frozen with a hash, and the implementing model only fills in the pass/fail columns. Just before ship, a script checks that record against the real runs.

### Every slice passes a review gate

When one slice is implemented and its checks pass, the agent starts a reviewer subagent in the same turn. The reviewer knows neither the main session's conversation nor earlier verdicts. It reads the plan, the diff and the repo's conventions, and returns findings.

<SliceLoopDiagram />

If there is a Critical or Important finding, the agent fixes it, runs the checks again, and sends it back to the same reviewer. This loop runs at most 3 times per slice. If the same issue comes back twice in a row, or all 3 rounds are used, it stops and reports to me.

When the gate passes, the slice is committed, its box is ticked, and the agent moves on to the next slice. It does not ask me between slices.

### It stops at a draft PR

With `/orch`, once the queue is empty the whole branch is reviewed once more (`/review --full`). The slice gate only sees one slice at a time, so problems that cross slices are caught here. This review starts `opus` and `sonnet` separately with the same brief and merges the two results.

Then `/ship` runs the closing gate. It runs every check in the plan again and checks the PASS records in the contract. If code that draws a screen changed, it runs screen QA (a browser for web). If logic changed and no test changed with it, it has the missing tests written. Just before the commit, it writes down the decisions and lessons from this work worth keeping (`/harvest`). Then it pushes the commits and opens a draft PR. The PR body lists each contract line with its verdict and evidence.

These are the lines left in the plan's `## Outcome` on the day I handed this site's home redesign to one `/orch` run.

```text title="PLAN-16-31-30.md — Outcome excerpt"
- contract: frozen 455d2935
- fix-loop: 01 iteration 1/3 (closed)
- review[01]: FAIL → PASS (fix 루프 1회) — Critical 0, Important 0 2026-10-31
- fix-loop: 02 iteration 1/3 (closed)
- review[02]: FAIL → PASS (fix 루프 1회) — Critical 0, Important 0 2026-10-31
- review: --full FAIL — Critical 1 (contract audit), Important 3 (빈 /blog 링크, 출처 없는 CI 문장, en 404 lang) · cross-model: sonnet · merged 2 · only opus 1 · only sonnet 1 · 2026-10-31
- contract: audit ok (3 checked rows at ab6fdec)
- status: shipped
```

Every gate passed in the end. Then I opened the draft PR and my verdict was that I could not tell what the site was about. The gates can measure whether a sentence matches its source, whether a link resolves, whether tests are green. They cannot measure who a home page speaks to, or what it says. That judgment is why the work stops at a draft PR. The home never shipped, and changing direction cost a few rewritten commits.

I start the merge with `/land`. It marks a draft ready, squash merges (in my personal repos), moves the base of stacked PRs, and cleans up the worktree in one go. If my request says "merge too" ("머지까지"), that phrase is the approval given in advance, so `/ship` merges right after it opens the PR.

### When several agents run

When there are two or more independent tasks, I use `/team`. The current Claude Code session becomes the lead and starts workers (Claude, pi, opencode, and a tester if needed) in [Herdr](./herdr.mdx) panes, giving each one task. Each worker walks the same path above on its own. A Claude worker merges its own S-size PRs; the lead merges the rest. An idle worker reads the repo through a lens such as security, logic, tests, CI, or performance to find the next task.

`/night` is the single-session, overnight version of those lenses. Until a deadline it reads the repo one lens at a time and writes down findings, then fixes only the S- and M-size ones with `/orch` and commits them to one night branch. When the run ends, it opens one draft PR from that branch and does not merge.

### One contract line

```text
- AC-1 · s01 · WHEN `pnpm build` finishes THE <file> SHALL <expected result> · check: s01-ac1 · status: FAIL · evidence: —
```

`check:` names a command in the plan's verification commands section. Only the `status` and `evidence` columns change during implementation. Evidence is the command that was actually run plus the one output line that backs the verdict.

## Check

The two scripts below live in `claude/hooks/` of the agent config repo, so they run only on a Mac linked to that repo.

1. Run every check in the plan. All of them must be green.

```sh
bash ~/.claude/hooks/verify-check.sh --plan .claude/<date>/PLAN-<time>.md --all   # verify-check: N/N green
```

2. Check that the contract's PASS records match the real run records.

```sh
python3 ~/.claude/hooks/ac-contract.py audit .claude/<date>/PLAN-<time>.md   # audit: ok
```

3. Check that the PR is open as a draft and not merged yet.

```sh
gh pr view --json isDraft,state   # {"isDraft":true,"state":"OPEN"}
```
