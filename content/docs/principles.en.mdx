Guides 01–06 cover what I set up and how. This one covers why. The principles come from the design notes (`docs/SKILL-PHILOSOPHY.md`) and working principles (`skills/_shared/principles/`) in the [agent config](./agent-config.mdx) repo, and from the incident log I keep for each rule (`docs/RULES-EVIDENCE.md`).

## A command instead of "done"

"It works" is not a criterion. When I hand off a task, the first line states what must be true when it is finished and the command that measures it.

```text
done: a draft PR is open · check: `pnpm check` · expect: check: ok
```

For larger tasks the plan file's Acceptance Contract extends that line. Each criterion pairs an observable condition (`WHEN … THE … SHALL …`) with the command that measures it, on one line. The contract goes through three steps.

1. **Falsify** — before implementing, run the command and confirm it is red. A criterion that is already green tells nothing apart, so the criterion gets fixed.
2. **Freeze** — when implementation starts, the criteria are fixed by a hash. Changing one means refreezing with a reason, and the review reads that reason.
3. **Self-assess** — the implementing model fills in only the verdict columns (status and evidence). Evidence is the command it actually ran plus the one output line the verdict rests on. "I checked" or "it is implemented" is not a pass; it is unverified. A check that ran but never hit its target (0 tests collected, a case skipped by a filter) is not a pass either.

A script then compares that self-report against the verification ledger. Before this format, plans listed success criteria as `- [ ]` lines. Nobody ran them, so "done" ended as the model's claim. I switched on 2026-10-15. What this stops is criteria quietly drifting. It does not stop forgery.

## The reviewer never sees the passing bar

A reviewer that knows the bar aims for it. It downgrades a Critical by one level to produce a "pass". Writing "ignore the bar" in the same file is not separation. So the bar is physically removed from the reviewer's context.

- The verdict rules live in a separate file that is read only after all findings are in.
- The reviewer that produces findings is a new subagent every time. It has not seen the conversation and reads only the plan and the diff. A re-review is a new spawn.

Reviews look along two axes: does it follow the repo's conventions (Standards), and did it build what the plan asked for (Spec fidelity). A diff with perfect conventions that builds the wrong thing still fails.

## Loops end on a deterministic check; weak criteria go to a person

A fix-and-recheck loop ends only on a deterministic check such as tests, lint, or typecheck. No loop ends because the model says "looks done". If the same issue comes back twice in a row, or three rounds go by without a pass, it stops and reports.

Design and scope have weak criteria, so they do not go in a loop. A person decides. Instead of asking every time, the agent picks the recommended option and lists it under "Auto-decided" in the draft PR body, where I review and change it. I do the merge.

## Fix a mistake in the layer that caused it

A mistake an agent could have avoided is feedback on the system around the diff before it is a bad diff. Fix only the code and the next run makes the same mistake. So I fix the layer that produced it: the spec, the domain vocabulary, the repo instructions, the validation, or the structure. A diff is used once; that layer is used on every later run. Without a signal, I do not write a rule in advance.

Each rule gets a dated entry in the incident log that says why it exists. The rule files keep only short imperatives; the reasons live in the log.

## Subtract before adding

The test is not line count but a deletion test. If removing something leaves the result the same, it was a duplicate; if the result changes, it was unique.

- I merged the three plan review lenses (product, design, engineering) into one, then split them again. Their personas, checklists, and verdict scales all differed, so removing one changed the result. The merged version measured a median of 46 turns and 22.4k output tokens, against 26 turns and 9.8k for a single lens.
- Call counts were weak evidence for deleting a skill. Most skills are not called by me; another skill points to them in its body. So I look at the reference graph. A skill that a live execution path points to stays; one only a catalog page points to goes.
- `package.json` scripts, config files, and `--help` output are the source of truth themselves. A document that restates them becomes a cache, and caches go stale. Docs hold only what an agent cannot look up: unwritten conventions, why a choice was made, and traps no setting reveals.

## Working principles

There are 19 short principle files, each read when its situation comes up. The rule file says only when to read each one; the body is read at that moment. These are the ones that come up most.

| Principle | When | What |
|---|---|---|
| verify-primary-source | Before writing a fact or number into a document | Did I read the primary source myself? If I only heard it, mark it unverified |
| fix-root-causes | Debugging, or before adding a guard or retry | Reproduce first. Ask "why" until the answer is a wrong decision in the code, not a consequence of one |
| attack-the-premise | Two fixes on one premise failed the same check | Before the third fix, write the shared premise as one sentence and test it directly |
| test-behavior-not-implementation | Writing or judging a test | Breaking the behavior must fail it; restructuring internals with the same results must pass it. Derive the expected value from the requirement |
| explain-the-number | Reporting a measurement | Ask "why not double?" and name the limiter. Keep the run count and spread next to the number |
| subtract-before-you-add | Extending a system, prompt, or rule set | Remove complexity first. Design for observed usage, not speculative edge cases |

## Check

To see whether the same principles hold in your own harness:

1. Write the done criterion for your next task as one command. Run it before implementing and confirm it is red. If it is green, the criterion measures nothing.
2. Look at the prompt you give the reviewer. If it contains a passing score or the verdict rules, the reviewer will aim for that bar.
3. Pick a rule you added recently and find where it says why it exists. If nowhere does, the next person cannot tell whether it is safe to delete.
