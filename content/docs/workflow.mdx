코딩 에이전트에게 일을 맡길 때는 매번 같은 길로 보내요. 작업 크기가 거칠 단계를 고르고, 플랜 파일이 할 일과 검증 기준을 들고, 슬라이스마다 리뷰 게이트를 지나고, draft PR 에서 멈춰요. 머지는 제가 해요. 단계 하나하나는 [에이전트 설정](./agent-config.mdx) 레포의 스킬(슬래시 명령)이에요. 그 레포는 비공개라서 그대로 쓸 수는 없고, 크기 표와 리뷰 루프 규칙은 원문을 아래에 실었어요.

## 동작 원리

### 크기가 단계를 골라요

모든 작업에 전체 단계를 돌리지 않아요. 바뀌는 파일 수로 크기를 정하고, 크기마다 거칠 단계가 정해져 있어요.

| 크기 | 기준 | 단계 |
|---|---|---|
| S | 파일 1~2개 | 구현 → 리뷰 → ship (버그면 원인 조사부터) |
| M | 파일 3~10개 | 탐색 → 플랜 → 슬라이스 루프 → 브랜치 전체 리뷰 → ship |
| L | 파일 10개 이상 | M 앞에 스코프 리뷰, 슬라이스 루프 뒤에 코드 정리(`/simplify`) 한 번이 붙어요 |
| XL | 무엇을 정해야 할지부터 모름 | 질문으로 결정을 먼저 푼 뒤 플랜 → L 과 같아요 |

파일 수가 적어도 인증, 인가, 사용자 입력, DB 쿼리, 파일 경로, 외부 API, 암호, 시크릿, 공개 API·계약을 건드리면 최소 M 이에요. 플랜의 슬라이스가 3개 이상이거나 새 모듈·서비스·패키지를 만들면, 플랜 뒤에 실행 관점 리뷰(`/plan-eng-review`)가 한 번 더 붙어요. 슬라이스 경계와 실패 경우를 코드 전에 잡는 편이 싸기 때문이에요.

`/orch` 를 쓰면 이 선택을 에이전트가 해요. 첫 줄에 작업 종류(추가·변경·버그·구조 정리), 크기, 완료 기준과 그것을 재는 명령을 한 줄로 선언하고, 그 단계들을 끝까지 이어요. 선언이 틀렸으면 그 줄을 보고 제가 고쳐요.

### 플랜은 파일이에요

M 이상은 플랜을 레포의 `.claude/<날짜>/PLAN-<시각>.md` 에 써요. 이 파일이 작업의 상태 전부예요. 세션이 끊기거나 컨텍스트가 압축돼도 파일을 다시 읽고 이어 가요.

- **슬라이스 큐** — 할 일을 수직 슬라이스로 나눈 표예요. 슬라이스 하나는 한 층의 조각이 아니라 끝에서 끝까지 동작하는 좁은 경로이고, 혼자 확인할 수 있어요. 체크박스가 진행 상태예요.
- **검증 계약** — 완료 기준을 한 줄씩 적고, 각 줄에 그것을 재는 명령을 묶어요. 구현 전에 계약 검사가 실제로 실패하는지 먼저 돌려 봐요. 처음부터 통과하는 계약 검사는 아무것도 재지 않기 때문이에요. 구현이 시작되면 계약을 해시로 고정하고, 구현하는 모델은 통과 여부 칸만 채워요. ship 직전에 스크립트가 그 기록을 실제 실행 기록과 대조해요.

### 슬라이스마다 리뷰 게이트를 지나요

슬라이스 하나를 구현하고 검증 명령이 통과하면, 같은 턴에 리뷰어 서브에이전트를 띄워요. 리뷰어는 메인 세션의 대화나 이전 판정을 모른 채 플랜과 diff, 레포 관례를 보고 발견 사항을 돌려줘요.

<SliceLoopDiagram />

Critical 이나 Important 가 있으면 고치고, 검증을 다시 돌리고, 같은 리뷰어에게 다시 보내요. 이 루프는 슬라이스마다 최대 3회예요. 같은 문제가 두 번 연달아 다시 나오거나 3회를 다 쓰면 멈추고 저에게 보고해요.

게이트를 통과하면 슬라이스를 커밋하고 큐에 체크한 뒤 다음 슬라이스로 넘어가요. 슬라이스 사이에 저에게 묻지 않아요.

### 마무리는 draft PR 에서 멈춰요

`/orch` 로 돌리면 큐가 빈 뒤 브랜치 전체를 한 번 더 리뷰해요(`/review --full`). 슬라이스 게이트는 슬라이스 하나씩만 보니, 슬라이스를 가로지르는 문제는 여기서 잡아요. 이 리뷰는 같은 지시서로 `opus` 와 `sonnet` 을 따로 띄워 두 결과를 합쳐요.

그다음 `/ship` 이 마무리 게이트를 돌아요. 플랜의 검증 명령을 전부 다시 돌리고 계약의 PASS 기록을 대조해요. 화면을 그리는 코드가 바뀌었으면 화면 QA(웹은 브라우저)를 돌리고, 로직이 바뀌었는데 테스트가 하나도 안 바뀌었으면 빠진 테스트를 쓰게 해요. 커밋 직전에는 이번 작업에서 남길 만한 결정과 배운 점을 노트로 적어요(`/harvest`). 그 뒤 커밋을 push 하고 draft PR 을 열어요. PR 본문에는 계약 줄마다 판정과 근거가 실려요.

이 사이트의 홈 재설계를 `/orch` 한 번에 맡긴 날, 플랜 파일의 `## Outcome` 에 남은 줄이에요.

```text title="PLAN-16-31-30.md — Outcome 발췌"
- contract: frozen 455d2935
- fix-loop: 01 iteration 1/3 (closed)
- review[01]: FAIL → PASS (fix 루프 1회) — Critical 0, Important 0 2026-10-31
- fix-loop: 02 iteration 1/3 (closed)
- review[02]: FAIL → PASS (fix 루프 1회) — Critical 0, Important 0 2026-10-31
- review: --full FAIL — Critical 1 (contract audit), Important 3 (빈 /blog 링크, 출처 없는 CI 문장, en 404 lang) · cross-model: sonnet · merged 2 · only opus 1 · only sonnet 1 · 2026-10-31
- contract: audit ok (3 checked rows at ab6fdec)
- status: shipped
```

게이트는 모두 통과했어요. 그런데 draft PR 을 열어 본 제 판단은 "이 사이트의 주제를 모르겠다"였어요. 게이트는 문장이 출처에 맞는지, 링크가 살아 있는지, 테스트가 초록인지를 잴 수 있어요. 홈이 누구에게 무슨 말을 하는 페이지인지는 재지 못해요. 그 판단 때문에 draft PR 에서 멈춰요. 그 홈은 배포하지 않았고, 방향을 바꾸는 비용은 커밋 몇 개를 다시 쓰는 것으로 끝났어요.

머지는 제가 `/land` 로 불러요. `/land` 가 draft 면 ready 로 바꾸고, squash 머지(개인 레포), 쌓인 PR 의 base 옮기기, worktree 정리를 한 번에 해요. 요청에 "머지까지"를 적으면 그 문구가 미리 한 승인이라서, `/ship` 이 PR 을 연 뒤 이어서 머지해요. 끝난 작업의 기록이 어디로 가는지는 [지식 루프](./knowledge.mdx) 가이드에서 다뤄요.

독립된 작업이 두 개 이상이면 `/team` 을 써요. 지금 Claude Code 세션이 팀장이 되고, 워커(Claude·pi·opencode, 필요하면 테스터)를 [Herdr](./herdr.mdx) pane 에 띄워 작업을 하나씩 맡겨요. 워커도 위와 같은 길을 혼자 걸어요. Claude 워커는 S 크기 PR 을 직접 머지하고, 나머지는 팀장이 머지해요. 일이 없는 워커는 보안·로직·테스트·CI·성능 같은 렌즈로 레포를 읽어 다음 일감을 찾아요.

`/night` 은 그 렌즈를 한 세션에서 밤새 돌리는 판이에요. 마감 시각까지 렌즈를 하나씩 읽으며 발견 사항을 적고, S·M 크기 작업만 `/orch` 로 고쳐 밤 브랜치 하나에 커밋해요. 런이 끝나면 그 브랜치로 draft PR 하나를 열고, 머지는 하지 않아요.

### 계약 한 줄의 모양

```text
- AC-1 · s01 · WHEN `pnpm build` 가 끝나면 THE <파일> SHALL <기대 결과> · check: s01-ac1 · status: FAIL · evidence: —
```

`check:` 는 플랜의 검증 명령 절에 있는 명령 이름이에요. 구현 중에는 `status`·`evidence` 두 칸만 바뀌어요. evidence 에는 실제로 돌린 명령과, 판정을 떠받치는 출력 한 줄을 적어요.

## 확인

아래 두 스크립트는 에이전트 설정 레포의 `claude/hooks/` 에 있어서, 그 레포를 연결한 맥에서만 돌아요.

1. 플랜의 검증 명령을 전부 돌려요. 모두 green 이어야 해요.

```sh
bash ~/.claude/hooks/verify-check.sh --plan .claude/<날짜>/PLAN-<시각>.md --all   # verify-check: N/N green
```

2. 계약의 PASS 기록이 실제 실행 기록과 맞는지 대조해요.

```sh
python3 ~/.claude/hooks/ac-contract.py audit .claude/<날짜>/PLAN-<시각>.md   # audit: ok
```

3. PR 이 draft 로 열려 있는지 봐요. 머지는 아직 안 된 상태여야 해요.

```sh
gh pr view --json isDraft,state   # {"isDraft":true,"state":"OPEN"}
```
