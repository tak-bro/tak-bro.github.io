I keep my coding agent config in one repo, `agent-config`. Three harnesses read it through symlinks: Claude Code, pi, and opencode. The repo is private, so you cannot clone it as is. The review subagent definition is shown in full below. The skill pipeline that takes one task from plan to merge is covered separately in the [Workflow](./workflow.mdx) guide.

## How it works

### Three harnesses read one repo

`install.sh` symlinks each part of the repo to the place its harness looks for it.

<HarnessRepoDiagram />

Two things are not in the drawing.

- The `opencode/*` links are made only when `~/.config/opencode` exists.
- Skills written by others are listed in `external-skills.txt`; `npx skills add -g` fetches only the missing ones into `~/.agents/skills`.

It links `~/.claude` item by item, not as a whole. `~/.claude` also holds machine state that Claude Code writes itself (session history, credentials). Linking the whole directory would put that state inside the repo.

`settings.json` and `settings.local.json` are not linked. Each is copied once, when it is missing. Claude Code rewrites both files in place. Instead, a hook reports the difference between the repo copy and the real `settings.json` when a session starts.

### One skill body, harness differences kept apart

The skills all three harnesses share (plan, implement, review, ship, and so on) have their body in one place, `agent-skills/<name>/SKILL.md`, written in English. pi and opencode read that file as is. On the Claude Code side, `claude/skills/<name>/SKILL.md` holds a line that says "read the canonical body first" and a table of only what differs in Claude Code (tool names, how skills are called, hook paths). This way a rule is not edited three times.

### Rules ask, hooks block

Rule files are instructions the model reads. Shared rules (git, commit messages, how to reply, coding discipline) live in one harness-neutral file, `RULES.md`. Claude Code imports that file from `CLAUDE.md`, and opencode reads the same file through `instructions` in `opencode.json`. pi keeps a shortened copy of the same rules in its own system prompt addendum. Only what differs per harness goes in a per-harness file.

The model can break a rule. What must not happen is blocked by a hook.

<HookGateDiagram />

The model reads the rules before it works; the hook is the safety net that catches a wrong try anyway.

A hook blocks only what one command can decide. "Open the PR as a draft, and merge only when I call `/land`" cannot be decided from a command, so it stays a rule only.

### Subagents pin their model

Exploring, reviewing, and performance analysis go to subagents. Each of the 9 subagent definitions sets `model:`. Only `reviewer`, which gives the verdict, is `opus`. The other 8 (exploring, simplifying, performance, design, and so on) are `sonnet`. Changing the main session's model does not change the subagents' cost or behavior.

The caller can override the pinned model for one call. Run solo, the whole-branch review (`/review --full`) starts `reviewer` with the same brief once as `opus` and once as `sonnet`, then merges the two results.

## My config

### Hooks

These are the main hooks set in Claude Code's `settings.json`.

| Event | Hook | What it does |
|---|---|---|
| PreToolUse (Bash, Monitor) | `deny-dangerous.sh` | Blocks commands that cannot be undone (see the denylist below). Also blocks the hook bypass flag `git commit --no-verify` |
| PreToolUse (Bash, Monitor) | `commit-convention.py` | Blocks a commit that is not in Conventional Commits format |
| PreToolUse (Bash) | `worktree-guard.py` | Blocks creating a branch with `git checkout -b` or `git switch -c` in the original checkout of a repo with an `origin`. Worktrees and subagents pass |
| PreToolUse (Bash) | `rtk-guarded.sh` | Rewrites a command into a form with shorter output, then checks the rewritten command against the denylist again |
| PreToolUse (Read, Bash) | `read-guard.sh` | Blocks reading a very large file whole. Reads with a range and subagents pass |
| PostToolUse | `tool-output-trim.sh` | Trims tool output over 1 KB |
| PostToolUse, PostToolUseFailure, Stop | `completion-gate.py` | Catches a "done" after code edits when no test, lint, or type check has passed |
| Stop | `review-gate.py` | Blocks a UX or UI review report that says "review complete" without evidence that the steps ran |
| PreCompact | `compact-gate.py` | Allows automatic context compaction only at a phase boundary (PR creation, merge, right after a slice passes review, and so on) |
| SessionStart | `settings-sync.py` | Reports the difference between the repo's `settings.json` and the real file. `--diff` shows it, and `--apply` backs up the real file and writes the repo's values over it |

In opencode, one plugin runs part of the same hook scripts (the denylist, commit format, output trimming, and so on) with the same input and the same exit 2 rule. pi runs copies of the hooks from its own extension.

### Command denylist

`deny-dangerous.sh` reads one file of regular expressions. It blocks only commands that cannot be undone, such as losing data, wiping a disk, or overwriting a protected branch. It does not block commands you can recover from, like `rm -rf node_modules` or `git clean`. Blocking too much makes the agent useless. This list is a seat belt, not a sandbox. It cannot stop a command written to slip past the patterns.

These are the categories it blocks now.

- `rm` aimed at root, the whole home folder, the whole `/Users` tree, or the root of a system directory (`/etc`, `/Library`, and so on). Deleting one file below them is not blocked
- The same deletion written another way: `find <root> -delete`, and `rmtree` or `rmSync` inside `python -c` or `node -e`
- Writing to raw disks, formatting, and erasing
- Fork bombs
- A force push that names a protected branch, and a force push with `--all`, `--tags`, or `--branches`
- Changing permissions or ownership across the whole system
- Deleting a repo with `gh` (API calls included), deleting secrets, SSH keys, or GPG keys, and making a repo public

### Few plugins and MCP servers on

Of the plugins other people wrote, I keep 9 on and 9 set to `false`. Every plugin on makes the skill list and the prompt longer, so they go on only when needed. The ones on are memory across sessions (`claude-mem`), terse chat replies (`caveman`), phone pushes and answers (`hwip`), Korean copy editing, UI work, research, video analysis, and Swift and C/C++ language servers.

There are five MCP servers (`codegraph`, `context7`, `mobile-mcp`, `figma-desktop`, `qmd`). Two of them are used in a particular way.

- **codegraph** — a graph with code symbols and call relations indexed ahead of time. One question replaces reading files one by one. A subagent does not use it unless told, so the delegation prompt says so.
- **qmd** — search over my notes and documents. A local daemon serves it over HTTP, so no session loads the embedding model again. It is the only MCP server pi and opencode get too.

Clone the repos on a new Mac and both lists are missing: `settings.json` holds only plugin names and on or off, and the MCP list lives in `~/.claude.json`. So the dotfiles install script reads both lists and adds back only what is missing. A server removed from the list is not unregistered, so a dropped server gets its own removal command.

### Review subagent

`reviewer` is the subagent that runs reviews. The caller's brief says what to look at, and this file only holds the constraints on how it runs. It does not change the code under review and only returns findings. The caller decides pass or fail.
